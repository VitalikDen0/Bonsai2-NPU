# Техническая архитектура и системная спецификация: Bonsai-NPU

## Аннотация

**Bonsai-NPU** — низкоуровневый runtime инференса, аппаратно оптимизированный для запуска 27-миллиардной гибридной языковой модели **Ternary-Bonsai-2-27B** на мобильных чипсетах Qualcomm Snapdragon. За счет синергии ультранизкобитного квантования (1-битные / тернарные веса), монолитного SMMU-маппинга памяти, аппаратно слитых векторных инструкций Hexagon (HVX), пакетного спекулятивного декодирования (MTP) и 4-битного динамического KV-кэша Turbo4 движок преодолевает ограничение пропускной способности мобильной памяти и обеспечивает генерацию в реальном времени.

> **Примечание об окружении тестирования:**  
> Эталонные аппаратные замеры проводились на смартфоне **OnePlus 13 (Snapdragon 8 Elite / SM8750, 16 ГБ LPDDR5X)** с включенными правами **Root**. Root-доступ использовался исключительно в целях низкоуровневой разработки: для ручной фиксации тактовых частот CPU/GPU/DRAM через узлы ядра `/sys/` (чтобы исключить влияние энергосберегающего троттлинга) и деплоя через ADB. Для пользовательской эксплуатации root-права **не требуются**.

## 1. Архитектурная база модели Bonsai 2 27B

Bonsai 2 27B построена на **гибридной архитектуре трансформера**, насчитывающей 64 слоя, в которой квадратичное внимание (Quadratic Self-Attention) заменено линейным рекуррентным пространством состояний везде, где это возможно:

* **Всего слоев**: 64 слоя.
* **Linear Attention (Delta-Net)**: 32 слоя. Использует рекуррентное ассоциативное состояние:
  `S_t = S_{t-1} + k_t · v_t^T`  
  Это полностью устраняет рост KV-кэша `O(N)` и обеспечивает константную вычислительную сложность `O(1)` на каждый шаг генерации.
* **Full Attention (GQA)**: 16 слоев. Grouped-Query Attention с 24 головами Query и 4 головами Key/Value, размерность головы `d_k = 256`, с ротационным кодированием позиций NeoX RoPE.
* **Слитые MLP блоки**: Активация SwiGLU (`Swish(x · W_gate) ⊙ (x · W_up)`) в связке с быстрым преобразованием Уолша-Адамара (FWHT-1024), устраняющим выбросы активаций (activation outliers) перед низкобитными матричными проекциями.
* **Размерности модели**: Скрытый слой `d_model = 5120`, промежуточный слой MLP `d_mlp = 17408`, размер словаря токенизатора `V = 248320`.

## 2. Аппаратные ограничения и физический предел памяти

### 2.1 Теоретический предел пропускной способности LPDDR5X
Процессор Snapdragon 8 Elite (SM8750) оснащен 4-канальной подсистемой памяти LPDDR5X-5300 с теоретической пиковой пропускной способностью:
```
BW_peak = 106.7 GB/s
```

В реальных условиях мобильного чипсета эффективный коэффициент шины памяти составляет около `η ≈ 87%`, что дает достижимую непрерывную скорость чтения:
```
BW_eff ≈ 92.8 GB/s
```

При квантовании Bonsai 2 27B в 1-битные / тернарные веса активный вес модели составляет:
```
M_weights = 3.405 GB (3.405 × 10^9 байт)
```

При последовательном декодировании по одному токену (`B = 1`) каждый параметр модели должен быть считан из DRAM в вычислительные блоки NPU ровно один раз за шаг:
```
T_floor = (3.405 × 10^9) / (92.8 × 10^9) ≈ 279.8 ms
```
Это абсолютный физический предел кремния для одиночного декодирования: **3.57 tok/s**.

### 2.2 Почему барьер 95.8% утилизации непреодолим в userspace Android
Первоначальная цель оптимизации составляла `≥ 95.8%` утилизации (`≤ 292 ms`). Экспериментальное профилирование на физическом устройстве выявило аппаратные и системные причины, делающие этот барьер недостижимым из пользовательского пространства:

1. **Блокировка мьютекса в ядре Linux (`fl->map_mutex`)**:
   Драйвер Qualcomm FastRPC (`drivers/soc/qcom/fastrpc.c`) защищает любые операции `fastrpc_mmap` глобальным мьютексом сессии `fl->map_mutex`. Когда фоновый поток процессора пытается асинхронно отображать страницы во время выполнения NPU GEMV в другом потоке, ядро блокирует ioctl вызовы NPU, и время слоя моментально вырастает с `1.5 ms` до `10.92 ms`.
2. **Конкуренция за шину LPDDR5X (Чтение против Записи)**:
   Контроллер памяти вынужден распределять такты между потоковым чтением NPU (`90 GB/s`) и сбросом кэша CPU/DMA-трансферами. Высокочастотные пакетные записи штрафуют циклы переключения шины LPDDR5X (`tWTR` / `tRTW`), добавляя неизбежные `60 ms` задержки на протяжении 64 слоев.

Таким образом, время **345 мс (81.1% от физического предела)** является практическим потолком для однотокенового шага (`B = 1`) в Linux/Android userspace.

## 3. Монолитная SMMU-архитектура (DMA-BUF Zero-Copy)

Вместо разбиения графа модели на отдельные подграфы или динамической подгрузки весов кусками через SMMU:
* Весь граф из 64 слоев (3.405 ГБ) отображается в единый непрерывный диапазон адресов SMMU через DMA-BUF при старте (`stage_init`).
* Раскладка памяти:
  * **Группа 0 (Слои 0–31)**: 1446 МБ
  * **Группа 1 (Слои 32–63)**: 1443 МБ
  * **Статический LM Head**: 322 МБ
  * **Арена кольцевого буфера**: 194 МБ
  * **Суммарный объем в SMMU**: **3405 МБ** (в пределах аппаратного лимита Qualcomm SMMU в 3680 МБ).
* Во время генерации системные вызовы ядра `mprotect`, `mmap` или `munmap` отсутствуют полностью. NPU обращается к весам напрямую по физическим указателям.

## 4. Конвейер векторного сопроцессора Hexagon DSP HVX

DSP Hexagon v79 выступает специализированным векторным ускорителем, берущим на себя все не-GEMV операции на всех 64 слоях.

```
       Хост (ARM64)                    Hexagon CDSP (HVX v79)
┌─────────────────────────┐         ┌──────────────────────────────┐
│  Токенизация и сэмплинг │         │ Пул из 4 потоков QuRT        │
│  Цикл оркестрации       │◄───────►│ 1024-битные векторные ядра   │
│  Диспетчеризация FastRPC│         │ (SwiGLU, RMSNorm, RoPE, FWHT)│
└─────────────────────────┘         └──────────────────────────────┘
            │                                      │
            ▼                                      ▼
┌──────────────────────────────────────────────────────────────────┐
│                   Вычислительные ядра Qualcomm NPU               │
│               Монолитный 1-битный / тернарный GEMV               │
└──────────────────────────────────────────────────────────────────┘
```

### 4.1 Распределение векторных регистров
HVX предоставляет 32 регистра по 1024 бита (128 байт) каждый (`v0`..`v31`). Все операции над активациями реализованы на нативных интринсиках Hexagon C (`Q6_V_...`):
* **RMSNorm**: Вычисляется через 8-полосную векторную редукцию (`Q6_Vqf32_vadd_Vqf32Vqf32`) с аппроксимацией обратного квадратного корня методом Ньютона-Рафсона.
* **NeoX RoPE**: Выполняется непосредственно в векторных регистрах для первых 64 размерностей головы с использованием комплексных инструкций поворота фазы.
* **FWHT-1024**: Слитое быстрое преобразование Уолша-Адамара выполняется в L1-кэше над блоками по 1024 числа перед проекцией MLP, предотвращая деградацию точности квантования.
* **Параллельное внимание GQA**: 4 рабочих потока под управлением QuRT (`qurt_sem_down` / `qurt_sem_up`) параллельно рассчитывают 24 головы Query и 4 головы Key/Value на аппаратных слайсах DSP.

## 5. Спекулятивное декодирование MTP (Multi-Token Prediction)

Поскольку генерация одиночного токена жестко упирается в пропускную способность памяти, единственный способ поднять скорость выше `3.5 tok/s` — это **амортизировать чтение 3.4 ГБ весов сразу на несколько токенов**.

### 5.1 Аппаратная пакетная верификация на NPU
В Bonsai-NPU реализована пакетная верификация (`forward_tokens_batch` и `cdsp_lmhead_batch`):
* При размере батча `B = 4` NPU считывает 3.4 ГБ весов из DRAM **всего один раз**.
* Выполняет GEMV для 4 токенов параллельно в исполнительных блоках NPU.
* Замер на OnePlus 13:
  ```
  T_verify(B = 4) = 380 ms  ==>  95 ms/токен  (10.52 tok/s)
  ```

### 5.2 Спекулятивный цикл драфта
```
   Шаг t:  Токены контекста
                │
                ▼
   ┌──────────────────────────┐
   │ Черновой драфт на CPU    │ ──► Выдвигает 3 кандидата (Prompt Lookup, dt < 2 мс)
   └──────────────────────────┘
                │
                ▼
   ┌──────────────────────────┐
   │ Пакетная верификация NPU │ ──► Считает логиты для всех 4 токенов (380 мс)
   └──────────────────────────┘
                │
                ▼
   ┌──────────────────────────┐
   │ Проверка совпадения      │ ──► Принимает k токенов (k от 1 до 4)
   └──────────────────────────┘
```

* **Генерация кандидатов**: Легковесный модуль Prompt Lookup / n-gram на CPU извлекает вероятные продолжения из недавнего контекста за время `< 2 ms` (без дополнительных нейросетевых параметров).
* **Верификация**: Батч из 4 кандидатов передается в `forward_tokens_batch`.
* **Эффективная скорость**:
  * При принятии 3 кандидатов: 4 токена генерируются за `380 ms` (эффективная скорость `10.5 tok/s`).
  * При средней энтропии текста (процент принятия 70–75%): Результирующая скорость составляет **5.5–8.0 tok/s**.

## 6. Динамический KV-кэш Turbo4 для длинного контекста

### 6.1 Отложенное выделение страниц (Demand-Paged Overcommit)
Классические движки заранее аллоцируют физическую память под максимальный размер контекста, что вызывает мгновенный сбой по памяти (OOM) на смартфонах. Bonsai-NPU решает эту проблему через виртуальный оверкоммит:
```c
kvk = (int8_t*)mmap(NULL, kv_sz, PROT_READ | PROT_WRITE,
                    MAP_ANONYMOUS | MAP_PRIVATE | MAP_NORESERVE, -1, 0);
```
* Виртуальный пул резервируется сразу под **262,144 токена**.
* Физическая память выделяется постранично ядром Linux только в момент физической записи токена в кэш.
* Потребление памяти строго пропорционально текущей длине диалога.

### 6.2 Сравнение форматов квантования и расхода памяти

| Длина контекста | Формат: FP16 (Стандарт) | Формат: Q8_0 / BF16 (Базовый) | Формат: Turbo4 (4-битный KV) |
| :--- | :---: | :---: | :---: |
| **Байт на токен** | 128 KiB | 64 KiB | **16 KiB** |
| **4,096 токенов** | 512 МБ | 256 МБ | **64 МБ** |
| **65,536 токенов** | 8.0 ГБ (OOM) | 4.2 ГБ (Нестабильно) | **1.05 ГБ** (Свободно помещается) |
| **262,144 токенов** | 32.0 ГБ (Сбой) | 16.8 ГБ (Сбой) | **4.1 ГБ** (Помещается в RAM смартфона) |

Turbo4 упаковывает каждую 256-мерную голову в 128 байт (два 4-битных ниббла на байт) с масштабирующими коэффициентами групп, открывая возможность работы с контекстом 65k–262k без исчерпания оперативной памяти мобильного устройства.

## 7. Модель безопасности, доступ к путям и работа без Root-прав

### 7.1 Доступ к `/data/local/tmp/`
Часто возникает вопрос: доступен ли каталог `/data/local/tmp/` без root-прав?

* **Через подключение ADB (с ПК)**: **ДА, ПОЛНОСТЬЮ ДОСТУПЕН**.  
  Каталог `/data/local/tmp` в Android имеет системные права `0777` или `1777` (`rwxrwxrwt`). При подключении через ADB команды выполняются от имени пользователя `shell` (`UID 2000`). Пользователь `shell` имеет полные права на чтение, запись и исполнение (`rwx`) файлов в `/data/local/tmp/` на любом серийном телефоне без root. Любой пользователь может отправить файлы через `adb push` и запустить `./bonsai_fwd`.
* **Локально на телефоне (без ПК, через Termux или приложение)**:  
  Начиная с Android 10, политика SELinux запрещает непривилегированным приложениям (`untrusted_app`) исполнять исполняемые файлы из каталога `/data/local/tmp` (политика W^X).  
  В этом случае запуск осуществляется из **собственного изолированного каталога приложения**:
  * В **Termux**: запуск выполняется в домашней директории пользователя:
    ```bash
    cd /data/data/com.termux/files/home
    ./bonsai_fwd bonsai27b-1bit.npubin tok.bin --server 8080
    ```
  * В **Android App (APK)**: библиотека `libbonsai_q1_skel.so` помещается в стандартную папку нативных библиотек `lib/arm64-v8a` приложения и загружается через `System.loadLibrary()`.

### 7.2 Архитектура FastRPC и управление производительностью
1. **Открытость для пользователей**:  
   Драйвер FastRPC (`/dev/fastrpc-cdsp`) и вендорные библиотеки (`/vendor/lib64/libcdsprpc.so`) по умолчанию открыты для всех пользовательских процессов Android. Доступ к Hexagon DSP не требует повышенных прав.
2. **Турбо-режим без Root**:  
   В релизных сценариях форсирование максимальных частот выполняется через штатный userspace API FastRPC:
   ```c
   HAP_power_request_t req;
   req.type = HAP_power_req_perf;
   HAP_power_set(NULL, &req);
   ```
   Этот вызов аппаратно запрашивает у контроллера питания Qualcomm максимальный профиль частоты для DSP и шины памяти.

## 8. Совместимость с БОЛЕЕ новыми и будущими поколениями чипов

Смогут ли пользователи запускать этот код на более новых процессорах Snapdragon?

**Да, смогут в полной мере, и производительность будет еще выше.**

1. **Обратная бинарная совместимость Hexagon**:  
   Qualcomm строго соблюдает обратную совместимость набора инструкций HVX (Hexagon Vector eXtensions). Байткод, скомпилированный под архитектуру **Hexagon v79** (Snapdragon 8 Elite), будет аппаратно исполняться на последующих версиях микроархитектуры (**Hexagon v81, v83 и новее** в Snapdragon 8 Elite Gen 2, Snapdragon 8 Gen 5 и др.).
2. **Стабильность системных интерфейсов FastRPC и QNN**:  
   Интерфейс Qualcomm FastRPC (`libcdsprpc.so`) и стандартизированный HAL нейропроцессора являются неизменной основой экосистемы Qualcomm Snapdragon Compute на протяжении многих поколений Android.
3. **Прямой выигрыш от более быстрой памяти**:  
   Поскольку монолитное ядро упирается в пропускную способность шины памяти, на будущих чипсетах с поддержкой **LPDDR5X-9600** или **LPDDR6** (свыше 130–150 ГБ/с) этот же самый бинарник автоматически покажет пропорциональный прирост скорости:
   * На 106.7 ГБ/с (Snapdragon 8 Elite): `345 ms/token` (`2.90 tok/s`).
   * На ~135 ГБ/с (будущие чипы): ожидается `~260 ms/token` (`~3.85 tok/s` в B=1 и `~10–12 tok/s` с MTP).
